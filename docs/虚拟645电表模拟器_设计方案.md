# 虚拟 DL/T 645-2007 电能表模拟器 — 设计方案

版本：v0.1（初版，用于指导开发，非最终冻结版）
面向读者：负责实现本项目的开发者 / AI 编码助手

---

## 1. 项目目标

开发一个软件形态的"虚拟电能表集群"，用于对接主站/集中器系统的开发联调与压力测试。核心要求：

1. **协议真实**：严格遵循 DL/T 645-2007 帧格式、控制码、DI 寻址、+33H 偏移、校验和规则。
2. **行为真实**：表内部有持续运行的仿真逻辑，电能量会随时间/负荷自动累加，最大需量会滚动更新，定时冻结会自动触发生成冻结数据，异常事件会在满足条件时自动生成——而不是一张静态的 DI→值查表。
3. **规模化**：单进程内并发运行最多 **2000** 个独立虚拟表实例，每个实例拥有独立地址、独立参数配置、独立运行状态。
4. **多通道**：同时支持串口（RS485 总线仿真，一条串口可挂多个地址）和 TCP（单口/多口，支持多客户端并发连接）两类通信方式接收报文，二者可同时对同一批表下发命令。
5. **可调试**：提供一条独立于标准协议的管理通道，支持直接修改表内部状态（时间、电能量、负荷模型等）及批量操作，用于快速构造测试场景，无需走标准协议的密码/权限流程。

非目标（本版本不做）：国网/南网各类基于 645 扩展的私有规约兼容（如 CSG1209022 等厂家/行业扩展，本项目严格限定在 DL/T 645-2007 标准文本范围内）、图形化管理界面（先做好命令行+配置文件+API）。

> 修订说明：负荷记录（DI3=06）历史存储与检索原先在 v0.1 中被列为非目标/后续可选项，现调整为**必须实现**的主线功能——见第12节。目标是完整覆盖 DL/T 645-2007 涉及的全部功能、帧格式与数据项，不再做协议子集裁剪。

## 2. 背景约束（协议要点摘要）

以下是驱动设计的关键协议约束，完整定义以以下资源为准，开发时逐项对照实现，不要凭记忆猜测字节格式：

- **DI 数据字典**：`../spec-engine/schema/dlt645-2007/dlt645.yaml`（完整的数据标识定义，包含所有DI编码、名称、长度、格式、单位）
- **协议参考**：`dlt645-2007` skill 参考资料（帧格式、控制码、校验规则等）

- 帧结构：`68H A0..A5 68H C L DATA CS 16H`，地址域 6 字节 BCD 低字节先传，前置 `FE FE FE FE` 唤醒前导。
- DATA 域每字节发送时 `+33H`，接收时 `-33H`；DI3DI2DI1DI0 低字节先传。
- 控制码 C 的功能码（读11H/写14H/冻结16H/改速率17H/改密码18H/需量清零19H/电表清零1AH/事件清零1BH 等）与对应正确/异常应答码。
- CS = 从首个 68H 到 DATA 结束的逐字节和，取低 8 位。
- 冻结量 DI3=05：DI2 区分定时冻结(00)/瞬时冻结(01)/时区表切换(02)/日时段表切换(03)；DI0 为第几次快照（定时冻结最近12次，瞬时冻结最近3次，循环覆盖）。
- 参变量 DI3=04 里的冻结数据模式字、负荷记录模式字、最大需量周期、滑差时间、时段表/费率表等是驱动仿真逻辑的关键配置项。
- 广播地址（全9）无应答；地址低位可用 AAH 做模糊查询，应答需回传真实完整地址。

## 3. 总体架构

```
                         ┌───────────────────────────┐
 Serial(总线, N个) ─解帧─▶│                            │
                         │   Router (地址路由)          │
 TCP(N个客户端)   ─解帧─▶│   精确 / 通配 / 广播 三种寻址   │──▶ mpsc 投递到目标表
                         │                            │◀── oneshot 回传响应帧
                         └───────────────────────────┘
                                      │
                                      │ 按地址查表
                                      ▼
                         ┌───────────────────────────┐
                         │   MeterRegistry             │
                         │   HashMap<地址, MeterHandle> │
                         └───────────────────────────┘
                                      │ 持有 handle
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
       MeterActor #1           MeterActor #2      ...   MeterActor #2000
       (独立 tokio task)        (独立 tokio task)          (独立 tokio task)
       ┌─────────────────┐
       │ select! 主循环     │◀── 全局 tick 广播 (broadcast channel)
       │ - on_tick          │
       │ - on_protocol_cmd  │
       │ - on_admin_cmd     │
       ├─────────────────┤
       │ MeterState         │  电能寄存器 / 瞬时量 / 最大需量 / 事件 / 冻结缓冲 / 参量
       ├─────────────────┤
       │ Simulation模块      │  虚拟时钟 / 负荷模型 / 脉冲累加 / 滑差窗口 / 事件检测 / 冻结调度
       └─────────────────┘
```

### 3.1 设计取舍说明（写进文档是为了防止后续被"优化"掉）

- **表状态不共享、不加锁**：每个虚拟表是一个独立 Actor（拥有独立 `MeterState`），只通过消息传递与外界交互。这不是性能妥协，而是刻意还原真实电表"单 MCU 主循环，命令排队串行处理"的行为，保证同一批命令重放时响应顺序确定、结果可复现。
- **I/O 并行，状态执行串行**：多个通信通道的字节收发/拆帧可以完全并发；但落到同一块表的命令最终都进入该表 Actor 的消息队列，由 Actor 单线程串行处理。跨表（2000个 Actor 之间）天然并行，互不影响。
- **走时用全局 tick 广播，不是每表一个定时器**：2000 个定时器没必要，一个全局 `broadcast` 通道统一节拍，也方便统一调节仿真时间倍率（测试时加速走时验证月结算/定时冻结）。
- **只读查询走旁路快照是可选的后续优化**，不在首版实现，先测出瓶颈再加（见第 9 节）。

## 4. 模块详细设计

### 4.1 Transport 层

职责：字节流 ↔ 完整协议帧的转换，不涉及表状态、不涉及地址路由决策（路由由 Router 做）。

- `trait FrameSource`：异步产出 `RawFrame { bytes, reply_channel }`，无论来自串口还是 TCP，对上层统一。
- `SerialChannel`：基于 `tokio-serial`。需处理：前导 `FE FE FE FE` 剥离、字节间超时拆帧（无固定长度分隔符，靠 68H...16H 匹配 + 帧间超时兜底）、串口参数（波特率）变更后需支持热切换（对应 17H 更改通信速率命令，仿真时如果该地址表被下发改速率命令，需要真实改变对应串口的运行参数，或至少在 admin 状态中如实反映"当前生效速率"，具体是否真的重开串口连接由部署形态决定，见 8.3 开放问题）。
- `TcpChannel`：基于 `tokio::net::TcpListener`，单端口支持多客户端并发连接（默认多路复用模式：一个连接上可能收到不同地址的帧，按帧内地址路由到不同表，模拟集中器代理场景）。可选独立端口模式：为特定表单独绑定端口（见 4.3 配置）。
- 帧校验（CS 不匹配、格式非法）：Transport 层本身不做协议语义校验，只做"能否切出一个候选帧"；帧内容合法性校验（含 CS）放在 Codec/Router 校验，校验失败按协议语义处理（读/写类命令有响应帧，用错误控制码+ERR字节；语法都不对的直接丢弃不响应，符合真实表行为）。

### 4.2 Frame Codec 与 DI 字典集成

无状态的纯函数模块，供 Router 和 MeterActor 复用：

- `decode_frame(bytes) -> Result<DecodedFrame, FrameError>`：解出地址、控制码、DATA（已做 -33H 还原）、并校验 CS。
- `encode_frame(address, control_code, data) -> Vec<u8>`：组帧、DATA 做 +33H、计算并附加 CS。
- `parse_di(data) -> (DI3, DI2, DI1, DI0, rest)`：从 DATA 中解出数据标识，供命令层进一步解析具体数据格式。
- **DI 数据字典加载**：
  - **复用 `spec-engine` 的解析能力**：`../spec-engine` 项目已实现完整的 YAML 解析和 DI 查询能力
  - **集成方式**：将 `spec-engine` 作为 workspace 成员或 git submodule，直接依赖其 DI schema 和解析器
  - **缺失字段补充**：YAML 中目前缺少 `writable`/`requires_auth` 字段，建议以下方案：
  
  **方案 A（推荐）**：在本项目中维护一个补充配置文件 `config/di_access_control.toml`：
  ```toml
  # DI 访问控制配置
  [[writable_di]]
  di_pattern = "0401****"  # DI3=04 DI2=01 全部可写（电表参数）
  requires_auth = 4        # 需要04级密码
  
  [[writable_di]]
  di_pattern = "0400****"  # DI3=04 DI2=00 部分可写
  requires_auth = 4
  
  [[writable_di]]
  di_pattern = "040002**"  # 时段表相关
  requires_auth = 4
  
  # 只读DI（默认所有DI3=00/01/02/03都是只读）
  # 无需显式配置
  ```
  
  **方案 B**：直接在代码中硬编码读写规则：
  ```rust
  fn is_writable_di(di: [u8; 4]) -> bool {
      match di[3] {  // DI3
          0x04 => true,   // 参变量类都可写
          0x03 => false,  // 事件记录只读
          0x05 => false,  // 冻结数据只读
          0x06 => false,  // 负荷记录只读
          _ => false,     // DI3=00/01/02 电能量只读
      }
  }
  
  fn required_auth_level(di: [u8; 4]) -> u8 {
      match di[3] {
          0x04 => 4,  // 写参数需要04级密码
          _ => 0,     // 只读操作不需要密码
      }
  }
  ```
  
- 该模块的正确性建议直接对照 skill 里第 10 节"Worked Example"写单元测试用例，逐字节比对。

#### 4.2.1 集成 spec-engine 的具体步骤

1. **添加依赖**（在 `Cargo.toml` 中）：
   ```toml
   [dependencies]
   # 方式1：workspace 成员
   spec-engine = { path = "../spec-engine/spec-engine" }
   
   # 方式2：直接依赖（如果spec-engine发布到了crates.io）
   # spec-engine = "0.1.0"
   ```

2. **加载 DI Schema**：
   ```rust
   use spec_engine::schema::DiSchema;
   
   lazy_static! {
       static ref DI_SCHEMA: DiSchema = {
           DiSchema::load_from_file("../spec-engine/schema/dlt645-2007/dlt645.yaml")
               .expect("Failed to load DI schema")
       };
   }
   
   fn lookup_di(di: [u8; 4]) -> Option<&'static DataItem> {
       let di_hex = format!("{:02X}{:02X}{:02X}{:02X}", di[3], di[2], di[1], di[0]);
       DI_SCHEMA.find_by_id(&di_hex)
   }
   ```

3. **读写权限检查**（使用方案B的硬编码规则）：
   ```rust
   fn handle_write_data(&mut self, di: [u8; 4], data: &[u8], password: &Password) 
       -> Result<Vec<u8>, WriteError> 
   {
       // 1. 检查DI是否可写
       if !is_writable_di(di) {
           return Err(WriteError::ReadOnly(di));
       }
       
       // 2. 检查密码权限
       let required_level = required_auth_level(di);
       if !self.check_password(password, required_level) {
           return Err(WriteError::PasswordIncorrect);
       }
       
       // 3. 查询DI定义（用于解析数据格式）
       let di_def = lookup_di(di).ok_or(WriteError::DiNotFound(di))?;
       
       // 4. 解析并写入
       self.write_di_value(di, data, di_def)?;
       
       Ok(encode_success_response())
   }
   ```

#### 4.2.2 数据块（通配查询）响应编码

当 DI2/DI1/DI0 包含 `FFH` 通配符时，响应格式为：

```
DATA = 原始请求DI(4字节) + m(1字节) + 数据项序列
数据项序列 = (DI0 DI1 DI2 DI3)₁ + 值₁ + (DI0 DI1 DI2 DI3)₂ + 值₂ + ...
```

其中 `m` = 实际匹配的子项数量（协议保证 ≤255），每个子项的 DI 是把通配符替换为实际值后的完整 4 字节标识。

**实现要点**：
- 遍历顺序：按 DI 的数值递增顺序返回（DI0 → DI1 → DI2 优先级递增）
- 空数据块：如果 `m=0`（无匹配项），返回 `DATA = 原始DI + 00H`，不是错误
- 超长数据块：如果编码后总长度 >200 字节，首帧返回能容纳的前 N 项，设置 C 的 D5=1，剩余部分由 12H 续传

```rust
fn encode_data_block_response(
    request_di: [u8; 4],           // 原始请求DI（含FFH通配符）
    items: Vec<([u8; 4], Vec<u8>)> // (实际DI, 值字节)
) -> Vec<u8> {
    let mut data = request_di.to_vec();
    data.push(items.len().min(255) as u8);  // m，协议保证不超255
    for (actual_di, value_bytes) in items {
        data.extend_from_slice(&actual_di);  // DI0 DI1 DI2 DI3
        data.extend(value_bytes);
    }
    data
}
```

#### 4.2.3 错误信息字（ERR）位定义

异常应答（控制码 D6=1）的 DATA = 1 字节 ERR，位定义：

```rust
bitflags::bitflags! {
    struct ErrorInfoWord: u8 {
        const OTHER           = 0b0000_0001;  // bit0 其他错误
        const NO_DATA         = 0b0000_0010;  // bit1 无请求数据（DI不存在）
        const PASSWORD_ERR    = 0b0000_0100;  // bit2 密码错/未授权
        const BAUD_LOCKED     = 0b0000_1000;  // bit3 通讯速率不能更改
        const TOU_ZONE_EXCEED = 0b0001_0000;  // bit4 年时区数超
        const TIME_SLOT_EXCEED= 0b0010_0000;  // bit5 日时段数超
        const RATE_EXCEED     = 0b0100_0000;  // bit6 费率数超
        // bit7 保留
    }
}

fn encode_error_response(address: &str, request_control_code: u8, err: ErrorInfoWord) -> Vec<u8> {
    let error_c = request_control_code | 0xC0;  // D7=1, D6=1
    encode_frame(address, error_c, &[err.bits()])
}
```

### 4.3 Router / MeterRegistry

```rust
struct MeterRegistry {
    by_address: HashMap<String, MeterHandle>,
}

struct MeterHandle {
    address: String,
    cmd_tx: mpsc::Sender<EngineMsg>,
}

enum EngineMsg {
    ProtocolCommand { frame: DecodedFrame, reply_tx: oneshot::Sender<Vec<u8>> },
    AdminCommand { cmd: AdminCommand, reply_tx: oneshot::Sender<AdminResponse> },
    UpdateAddress { old: String, new: String },  // 15H 写通信地址时的内部消息
}
```

职责：
1. 收到 `DecodedFrame` 后判断地址类型：
   - **精确地址** → 查 `by_address`，未命中则丢弃不响应（真实总线上没有这块表）。
   - **通配地址（低位含 AAH）** → 线性扫描匹配的表（2000 量级下线性扫描足够快，不建立额外索引），命中的每一个都独立处理并各自应答（真实场景下这属于模糊查询，多表匹配是否都应答由配置项决定，默认全部应答，测试者可自行判断合理性）。
   - **广播地址（全 9，即 6 字节全为 `99H`）** → **仅当控制码为 08H（广播校时）或 16H（广播冻结）时** fan-out 给所有表 Actor，其他控制码静默丢弃；广播命令**不等待、不回传响应**（协议规定广播命令无应答）。
2. 把匹配到的 `EngineMsg::ProtocolCommand { decoded_frame, reply_tx }` 送进目标表 Actor 的 mpsc 队列。
3. 收到 Actor 回传的响应帧后，通过发起该请求的 Transport 连接原样写回（Router 需要记录"这条请求是从哪个物理连接来的"，靠 Transport 层传入的 `reply_channel` 闭包/oneshot 完成，不需要 Router 自己维护连接表）。

**地址判断辅助函数**：

```rust
fn is_broadcast_address(addr_bytes: &[u8; 6]) -> bool {
    addr_bytes.iter().all(|&b| b == 0x99)
}

fn is_wildcard_address(addr_bytes: &[u8; 6]) -> bool {
    addr_bytes.iter().any(|&b| b == 0xAA)
}

fn validate_broadcast_command(control_code: u8) -> bool {
    matches!(control_code, 0x08 | 0x16)  // 仅允许广播校时和广播冻结
}

fn match_address(pattern: &[u8; 6], actual: &[u8; 6]) -> bool {
    pattern.iter().zip(actual.iter()).all(|(p, a)| *p == 0xAA || *p == *a)
}
```

Admin 通道的批量操作也经过本模块的地址匹配逻辑复用（地址范围/正则/全部），避免重复实现两套地址匹配代码。

### 4.4 全局 Tick 广播

```rust
let (tick_tx, _) = broadcast::channel::<TickEvent>(16);

struct TickEvent {
    wall_elapsed: Duration,   // 距上次 tick 的真实耗时
    time_scale: f64,          // 当前仿真时间倍率，可被 admin 命令动态调整
}
```

单独一个 `tokio::spawn` 任务以固定周期（建议 1s，可配置）产出 tick 广播，2000 个表 Actor 各自持有一个 `broadcast::Receiver` 订阅。`time_scale` 允许全局或分组调整（比如"这一批表加速走时做压测，另一批保持正常速度做联调"，可以按需要开多个 tick 广播组，默认一组）。

### 4.5 MeterActor（单表核心）

```rust
async fn run(mut self) {
    loop {
        select! {
            Ok(tick) = self.tick_rx.recv() => self.on_tick(tick),
            Some(msg) = self.cmd_rx.recv() => match msg {
                EngineMsg::ProtocolCommand { frame, reply_tx } =>
                    self.on_protocol_command(frame, reply_tx),
                EngineMsg::AdminCommand { cmd, reply_tx } =>
                    self.on_admin_command(cmd, reply_tx),
            }
        }
    }
}
```

#### 4.5.1 on_tick —— 仿真推进，按固定顺序执行（后续步骤依赖前面结果）

1. **虚拟时钟推进**：`virtual_time += wall_elapsed * time_scale`。虚拟时钟是表状态的一部分，不直接用系统时间——这样"校时"命令（04 00 01 02 / 08H广播校时）才能真实生效，且支持测试时调速。
2. **负荷模型取瞬时量**：按当前配置的负荷模型（固定值 / 正弦波动 / 随机游走 / 外部曲线文件插值）计算 A/B/C 相电压、电流、功率因数，推导出瞬时有功/无功/视在功率。
3. **脉冲累加电能量**：不用浮点直接"功率×时间"累加（长期运行有漂移），采用脉冲计量模型——按电表常数（04 00 04 09，imp/kWh）把瞬时功率积分成脉冲增量，凑够一个脉冲整数才进位到电能寄存器，行为上贴近真实电能表的计量原理。按虚拟时钟当前时刻查时段表得出费率号（**查哪一套时段表由"周休日特征字"04 00 08 01 决定当天是工作日还是休息日，再决定用第一套/第二套日时段表**，两套时段表之间还可能存在"切换时间"04 00 00 06/07 配置的定期切换），分别计入对应费率的电能寄存器（总/分相/分费率、正向/反向、有功/无功/视在均需要）。**"组合有功总电能"（DI2=00）不是独立寄存器，而是按"有功组合方式特征字"（04 00 06 01）配置的加减规则，由正向/反向有功实时组合算出**（无功组合1/2同理按各自特征字，四象限加减组合）——这一步之前版本遗漏了，现补充为 tick 中的派生计算，不单独存储组合总电能的脉冲累加状态，避免和分量电能账目不一致。
4. **最大需量滑差窗口**：按参数里的需量周期 + 滑差时间做滑动平均，超过历史最大值则更新最大需量寄存器及发生时间。
5. **事件检测**：电压/电流/功率因数等超出配置阈值时，生成对应 03 类事件记录（失压/欠压/过压/断相/过流/过载等），写入事件环形缓冲（区分总计次数+持续时长 与 最近若干次详情记录两部分，对应协议 DI0=00 汇总 / DI0=01..0A 明细两种查询）。**同一步同时刷新"电表运行状态字1-7"（04 00 05 01-07）**——这些状态字本身也是派生量（电池电压是否欠压、功率方向、各相故障标志位等直接由本次 tick 算出的瞬时量和事件状态映射得到，不需要额外单独维护一份"事实来源"，见 4.6.1）。
6. **冻结调度检查**：读该表的冻结数据模式字配置的周期模式（协议定义的几种特殊模式：按月/按日/按小时/瞬时），到点即对当前电能量/最大需量/瞬时变量做一次快照，写入对应 DI2 分类下的 DI0 环形缓冲（定时冻结 05 00 最近12次滚动覆盖）。
7. **负荷记录采样调度**：按"负荷记录模式字"（04 00 09 01）启用的数据类别 + 各通道独立配置的记录间隔时间（04 00 0A，第1-6类负荷各自的 NNNN 分钟间隔），到点对总加通道(00)及已启用的负荷类别(01-06)分别生成一条负荷记录，写入负荷记录时序表——详见第12节，这是与冻结快照（固定槽位滚动覆盖）完全不同的、按时间序列追加的数据模型。

#### 4.5.2 on_protocol_command —— 标准协议命令处理

1. 按控制码 C 路由到对应 handler（读数据 11H/读后续数据 12H/读通信地址 13H/写数据 14H/写通信地址 15H/冻结命令 16H/改通信速率 17H/改密码 18H/需量清零 19H/电表清零 1AH/事件清零 1BH）。

2. **权限与密码校验**（仅涉及写操作/权限的命令）：
   - 写数据（14H）、最大需量清零（19H）需要 **04 级**权限
   - 电表清零（1AH）、事件清零（1BH）需要 **02 级**权限
   - 校验失败按对应异常控制码 + ERR 错误字（`ErrorInfoWord::PASSWORD_ERR`）返回

3. **读数据（11H）**：按 DI3DI2DI1DI0 定位到状态字段（仿真量直接读当前值，参量直接读配置字段），支持数据块通配（DI2/DI1/DI0=FFH）批量返回（编码规则见 4.2.1）。
   - **特殊处理：负荷记录（DI3=06）** 的读取需要解析时间范围参数：
     ```rust
     fn handle_read_data(&self, data: &[u8]) -> Result<Vec<u8>, ReadError> {
         let di = [data[0], data[1], data[2], data[3]];
         
         match di[3] {  // DI3
             0x06 => {  // 负荷记录，需要特殊处理
                 if data.len() < 14 {
                     return Err(ReadError::InvalidDataLength);
                 }
                 let start_time = parse_bcd_time(&data[4..9])?;   // mm hh DD MM YY
                 let end_time = parse_bcd_time(&data[9..14])?;
                 self.read_load_profile(di, start_time, end_time)
             }
             _ => {  // 普通DI查询
                 self.read_normal_data_item(di)
             }
         }
     }
     ```

4. **读后续数据（12H）多帧续传**：读命令（11H）响应数据超过 L≤200 字节上限时（典型场景：通配数据块查询、大段负荷记录/事件明细一次性拉取），Actor 需要把完整结果暂存为一个"待续传缓冲"：

   ```rust
   struct PendingContinuation {
       full_data: Vec<u8>,          // 完整响应数据（已编码，含DI+数据）
       next_offset: usize,          // 下次续传的起始位置
       created_at: Instant,         // 用于过期检测
       max_fragment_size: usize,    // 单片最大字节数（200 - DI(4) - SEQ(1) = 195）
   }
   
   // 键：(连接ID的抽象, DI3DI2DI1DI0)，不包含SEQ（SEQ是递增的）
   type ContinuationCache = HashMap<(ConnectionId, [u8; 4]), PendingContinuation>;
   ```

   - **首帧（11H 响应）**：如果数据 >200 字节，返回前 N 字节 + 设置 C 的 D5=1（有后续数据标志）
   - **续传帧（12H 请求）**：DATA = `DI0 DI1 DI2 DI3 SEQ`（5 字节），响应 DATA = `DI0 DI1 DI2 DI3 SEQ + 数据片段`
   - **SEQ 校验**：SEQ 从 1 开始递增，不连续或缓冲过期（建议 60 秒超时）则返回错误并清理缓冲
   - **最后一片**：D5=0 表示无后续，清理该缓冲

5. **读通信地址（13H）**：
   - 请求 DATA = 空（L=0）
   - 响应 DATA = 6 字节地址域（A0..A5），**注意：地址字节不做 +33H 偏移**（协议明确规定的例外）
   - 异常情况**无应答**（不返回错误码）
   
   ```rust
   fn handle_read_comm_address(&self, reply_tx: oneshot::Sender<Vec<u8>>) {
       let raw_address_bytes = self.state.address_as_bcd_bytes();  // [u8; 6]
       // 注意：此处编码时需跳过常规的 +33H 偏移
       let response_frame = encode_frame_no_offset(
           &self.state.address,
           0x93,  // 正确应答
           raw_address_bytes.to_vec(),
       );
       reply_tx.send(response_frame).ok();
   }
   ```

6. **写数据（14H）**：
   - DATA 格式：`DI0 DI1 DI2 DI3 + PA0 P00 P10 P20 + C0 C1 C2 C3 + 数据`
   - 密码字段：4 字节 `PA0 P00 P10 P20`，PA0 高半字节 = 权限等级（00-09），低半字节+P00 P10 P20 = 3.5 字节密码值
   - 操作者代码：4 字节 BCD
   - 写入成功后，追加一条编程记录事件（03 30 0F 01 费率参数表编程记录，或对应的其他编程记录类别）

7. **写通信地址（15H）需要联动 Registry**：
   
   ```rust
   async fn handle_write_comm_address(
       &mut self,
       new_address: String,
       reply_tx: oneshot::Sender<Vec<u8>>,
       registry_tx: mpsc::Sender<RegistryMsg>,
   ) -> Result<(), WriteError> {
       // 1. 通知 Registry 预检查新地址是否冲突
       let (check_tx, check_rx) = oneshot::channel();
       registry_tx.send(RegistryMsg::CheckAddressConflict {
           new_address: new_address.clone(),
           reply: check_tx,
       }).await?;
       
       if check_rx.await? {
           // 冲突，协议要求无应答（不返回错误码）
           return Err(WriteError::AddressConflict);
       }
       
       // 2. 修改本地状态
       let old_address = self.state.address.clone();
       self.state.address = new_address.clone();
       
       // 3. 用**新地址**构造响应帧（协议要求）
       let response = encode_frame(&new_address, 0x95, vec![]);
       reply_tx.send(response).ok();
       
       // 4. 通知 Registry 更新路由表（异步，不阻塞响应）
       registry_tx.send(RegistryMsg::UpdateAddress {
           old: old_address,
           new: new_address,
           meter_handle: self.handle.clone(),
       }).await?;
       
       Ok(())
   }
   ```

8. **冻结命令（16H）**：
   - 请求 DATA = 4 字节 `mm hh DD MM`（分时日月，BCD）
   - 特殊模式（广播冻结）：
     - `99 DD hh mm` = 按月周期冻结
     - `99 99 hh mm` = 按日周期冻结
     - `99 99 99 mm` = 按小时周期冻结
     - `99 99 99 99` = 瞬时冻结
   - **广播冻结（16H + 广播地址 999999999999H）语义**：立即执行一次瞬时冻结，**不修改**表的冻结模式字（04 00 09 02-06）配置
   - **单播冻结**：按 DATA 中的参数立即执行一次对应模式的冻结
   - **响应**：成功 L=0（空 DATA），失败 L=1 + 1 字节错误码

9. **广播校时（08H）**：
   - 请求 DATA = 6 字节 `ss mm hh DD MM YY`（BCD，低字节先传）
   - **注意**：广播校时的 DATA 也需要做 **+33H 偏移**（所有 DATA 区统一规则，无例外）
   - 响应：广播命令无应答
   - 生效：所有表收到后立即将虚拟时钟调整为指定时间
   
   ```rust
   fn handle_broadcast_time_sync(&mut self, data: &[u8]) -> Result<(), TimeError> {
       if data.len() != 6 {
           return Err(TimeError::InvalidLength);
       }
       // DATA 已在 Codec 层做了 -33H 还原
       let ss = bcd_to_decimal(data[0])?;
       let mm = bcd_to_decimal(data[1])?;
       let hh = bcd_to_decimal(data[2])?;
       let dd = bcd_to_decimal(data[3])?;
       let month = bcd_to_decimal(data[4])?;
       let yy = bcd_to_decimal(data[5])?;
       
       self.state.virtual_time = DateTime::parse_from_bcd(yy, month, dd, hh, mm, ss)?;
       Ok(())
   }
   ```

10. **更改通信速率（17H）**：
   - 请求 DATA = 1 字节通信速率特征字
   - **实现策略**（见配置项 `allow_baud_change`）：
     - **方案 A（默认）**：如果串口上挂载多个地址，返回错误 D7H + `ErrorInfoWord::BAUD_LOCKED`
     - **方案 B**：如果串口只挂载一个地址，允许执行，记录到表状态并通知 Transport 层真实切换串口参数
     - **方案 C（仿真模式）**：正常应答，只在表状态里标记"协议生效速率"，不真实切串口硬件
   
   ```toml
   # 配置文件中的开关
   [[transport.serial.devices]]
   path = "/dev/ttyUSB0"
   allow_baud_change = false  # true=允许17H真实切速率（需确保单地址）
   ```

10. **修改密码（18H）**：
    - 请求 DATA（L=0CH，12 字节）：
      ```
      DI0 DI1 DI2 DI3 (固定为 04 00 02 01-0A，对应密码级别1-10)
      + PA0 P00 P10 P20  (旧密码，PA0=权限等级)
      + PAN P0N P1N P2N  (新密码，PAN=新密码的权限等级)
      ```
    - PA0、PAN 取值范围：00-09（00 最高权限，数值越大权限越低）
    - 校验：旧密码必须正确，且权限 ≥ 目标密码等级（即只能修改自己权限或更低权限的密码）
    - 成功后追加编程记录（03 30 12 01 密钥更新记录）

11. **时段表切换逻辑**：
    - **两套时段表切换时间**：
      - `04 00 01 06`：两套**时区表**切换时间（YYMMDDhhmmss，12字节BCD）
      - `04 00 01 07`：两套**日时段表**切换时间（YYMMDDhhmmss，12字节BCD）
    - **周休日特征字**（04 00 01 01）：YYMMDDWW（年月日星期，WW=0 表示星期天）
    - **当前日期时间**：
      - `04 00 01 01`：YYMMDDWW（年月日星期）
      - `04 00 01 02`：hhmmss（时分秒）
    
    切换逻辑：
    ```rust
    fn get_active_tou(&self) -> &TouConfig {
        // 1. 检查是否到达切换时间（04 00 01 06/07）
        if let Some(switch_time) = self.tou.switch_datetime {
            if self.virtual_time >= switch_time {
                // 触发切换并生成冻结快照（DI2=02/03）
                // 更新 current_active_table
            }
        }
        
        // 2. 根据周休日特征字判断当天是工作日还是休息日
        // 注意：周休日特征字存储的是一个固定日期+星期，用于标记"哪些星期"是休息日
        // 实现时需要提取 WW 字段，判断当前虚拟时钟的星期数是否匹配
        
        let day_of_week = self.virtual_time.weekday();
        let is_rest_day = self.check_is_rest_day(day_of_week);
        
        if is_rest_day {
            &self.tou.slot_table_2
        } else {
            &self.tou.slot_table_1
        }
    }
    ```

12. **清零类命令的范围定义**（协议文本描述较简略，以下为实现约定）：
    - **需量清零（19H）**：仅重置最大需量寄存器及发生时间，不影响电能量累计；追加编程记录 03 30 xx（待明确具体 DI）
    - **电表清零（1AH）**：重置电能寄存器、最大需量为 0（相当于表恢复出厂电量状态），但**保留**事件记录、冻结历史、参量配置（时段表/密码等）；追加编程记录 03 32 01 01（上 1 次购电日期等，见图片）
    - **事件清零（1BH）**：清空 `event_records` 明细与 `event_summary` 计数，但操作本身要在编程记录类别里追加一条日志——这条日志属于操作类事件，不在本次清零范围内

13. 写操作生效后，追加对应的编程记录事件（03 30 xx 系列），保证"读事件记录"与"实际发生的写操作"是联动一致的。

14. **模拟真实响应时延**：处理完成后延迟一个随机值（20~500ms 区间，符合协议 Td 描述）再通过 `reply_tx` 回传响应帧，让抓包行为更接近真实设备（可通过配置关闭，压测场景下可能需要去掉延迟）。

#### 4.5.3 on_admin_command —— 调试通道命令

跳过密码/权限校验，直接读写状态或触发动作，典型命令：
- `set_time` / `set_time_scale`
- `set_register(di, value)` 直接改任意寄存器
- `set_load_model(profile)` 切换负荷模型
- `force_freeze(trigger_type)` 立即触发一次冻结快照
- `force_event(event_type)` 手动注入异常事件
- `set_password(level, value)`、`set_status_bit(...)`

Admin 命令走同一个 Actor 消息队列，因此不会与协议命令产生状态竞态，只是可以"插队"，符合"多来源中断进同一个主循环"的真实语义。

### 4.6 MeterState 数据结构（草案）

```rust
struct MeterState {
    // ─────────────────────────────────────────────────────────────
    // 身份与参量（可被写命令/admin命令修改）
    // ─────────────────────────────────────────────────────────────
    address: String,
    
    // 密码：10 级（00-09），每级密码 = 权限等级(1字节高半字节) + 密码值(3.5字节)
    passwords: [PasswordLevel; 10],
    
    // 时段表配置（两套日时段表，支持切换）
    tou: TouConfig,
    weekly_rest_day_word: u8,       // 04 00 08 01 周休日特征字，决定按日历日选用第一/二套日时段表
    
    // 能量组合方式特征字（参量，可写）
    active_energy_combination_word: u8,   // 04 00 06 01 有功组合方式特征字
    reactive_combination_words: [u8; 2],  // 04 00 06 02/03 无功组合方式1/2特征字
    
    // 结算日配置
    settlement_days: [u8; 3],       // 最多3个结算日（或 9999 表示未设置）
    
    // 需量计算参数
    demand_period: Duration,        // 04 00 04 04/05 需量周期
    sliding_window: Duration,       // 04 00 04 06/07 滑差时间
    
    // 冻结与负荷记录配置
    freeze_mode_word: FreezeModeWord,       // 04 00 09 02/03/04 定时/瞬时/约定冻结模式字，见 4.6.2
    load_record_mode_word: LoadRecordModeWord,  // 04 00 09 01 负荷记录模式字，见 4.6.3
    load_record_intervals: [u16; 6],  // 04 00 0A 01-06，第1-6类负荷记录间隔（分钟）
    
    // 电表物理参数
    meter_constant: u32,            // 04 00 04 09，imp/kWh
    rated_voltage: u32,             // 04 00 04 01，额定电压（毫伏存储）
    rated_current: u32,             // 04 00 04 02，额定电流（毫安存储）
    
    // 通信参数
    comm_baud: [BaudRate; 5],       // 04 00 04 0A，各通信口速率特征字

    // ─────────────────────────────────────────────────────────────
    // 虚拟时钟（表内独立时间，非系统时间）
    // ─────────────────────────────────────────────────────────────
    virtual_time: DateTime<Utc>,
    time_scale: f64,                // 仿真时间倍率

    // ─────────────────────────────────────────────────────────────
    // 仿真量：电能寄存器，按 (能量类型, 费率, 结算日) 索引
    // ─────────────────────────────────────────────────────────────
    energy_registers: HashMap<(EnergyKind, RateIndex, SettlementDay), Decimal>,
    pulse_accumulator: HashMap<EnergyKind, u64>,  // 脉冲累加中间态，未凑够一整脉冲的余量

    // ─────────────────────────────────────────────────────────────
    // 仿真量：瞬时变量（每 tick 刷新）
    // ─────────────────────────────────────────────────────────────
    instant: InstantVars,           // 电压/电流/功率/功率因数/频率/温度等

    // ─────────────────────────────────────────────────────────────
    // 最大需量
    // ─────────────────────────────────────────────────────────────
    max_demand: HashMap<(DemandKind, RateIndex), (Decimal, DateTime<Utc>)>,
    demand_sliding_window: SlidingWindow,  // 滑差窗口状态

    // ─────────────────────────────────────────────────────────────
    // 事件记录（环形缓冲）
    // ─────────────────────────────────────────────────────────────
    // Key = (EventKind=DI2, SubKind=DI1)，例如：
    // - (01, 01) = A相失压事件
    // - (30, 0F) = 费率参数表编程记录
    // - (32, 01) = 第1次购电记录
    event_records: HashMap<(EventKind, SubKind), RingBuffer<EventRecord>>,  // 最近10次明细
    event_summary: HashMap<(EventKind, SubKind), EventSummary>,  // 总次数+总时长（编程记录的总时长为0）

    // ─────────────────────────────────────────────────────────────
    // 冻结数据（环形缓冲，按触发类型分别维护）
    // ─────────────────────────────────────────────────────────────
    freeze_snapshots: HashMap<FreezeTrigger, RingBuffer<FreezeSnapshot>>,

    // ─────────────────────────────────────────────────────────────
    // 负荷记录（时序表，非环形缓冲）
    // ─────────────────────────────────────────────────────────────
    // 注意：负荷记录不在内存中维护完整历史，只在 tick 时生成新记录并立即落库
    // 读取时直接查询 SQLite 的 load_profile_records 表
    load_profile_next_record_time: HashMap<LoadChannel, DateTime<Utc>>,  // 下次采样时间

    // ─────────────────────────────────────────────────────────────
    // 负荷模型配置
    // ─────────────────────────────────────────────────────────────
    load_model: LoadModel,

    // ─────────────────────────────────────────────────────────────
    // 派生状态字（见 4.6.1）
    // ─────────────────────────────────────────────────────────────
    derived_status_words: DerivedStatusWords,
}

// ─────────────────────────────────────────────────────────────
// 辅助类型定义
// ─────────────────────────────────────────────────────────────

struct PasswordLevel {
    level: u8,           // 00-09，00最高权限
    password: [u8; 3],   // P0 P1 P2（实际是3.5字节，P2只用低4位）
}

struct EventSummary {
    total_count: u32,
    total_duration_minutes: u32,
}

enum LoadChannel {
    Total,      // 00 总加
    Load1,      // 01 第1类负荷
    Load2,      // 02
    Load3,      // 03
    Load4,      // 04
    Load5,      // 05
    Load6,      // 06
}

/// 04 00 05 01~07 电表运行状态字、04 00 06 01~03 组合方式特征字、04 00 08 01 周休日特征字
/// 等一律建模为"派生量"：由 instant（瞬时量）、events（故障状态）、tou（当前生效时段表）
/// 等其余权威字段在每次 tick/事件更新后重新计算刷新，本身不是可被写命令直接修改的独立数据
/// （组合方式特征字、周休日特征字例外——它们是可配置参量，写命令可改，改了之后会反过来影响
/// 状态字1/2的计算结果和电能量组合逻辑，因此在 MeterState 里实际存放位置是"参量区"，这里的
/// DerivedStatusWords 只缓存"运行状态字1-7"这类纯运行时只读状态）
struct DerivedStatusWords {
    status_word_1: u16,          // 需量方式/电池状态/有无功功率方向
    status_word_2: u16,          // 分相有功/无功功率方向
    status_word_3: u16,          // 当前时段表套别/供电方式/编程允许/继电器状态
    status_word_4_6: [u16; 3],   // A/B/C 相故障状态
    status_word_7: u16,          // 合相故障状态（逆相序/不平衡/辅助电源失电/掉电/需量超限）
}
```

#### 4.6.1 派生状态字的计算时机

派生状态字在以下时机重新计算：
1. **每次 tick 结束后**（瞬时量、功率方向已刷新）
2. **事件生成/结束时**（故障状态位需要更新）
3. **时段表切换时**（状态字 3 的"当前时段表套别"位需要更新）

不在响应读命令时临时计算，避免重复遍历状态。

#### 4.6.2 FreezeModeWord 结构定义

冻结模式字有多个 DI 编码，分别控制不同类型的冻结：
- **04 00 09 02**：定时冻结数据模式字
- **04 00 09 03**：瞬时冻结数据模式字  
- **04 00 09 04**：约定冻结数据模式字
- **04 00 09 05**：整点冻结数据模式字
- **04 00 09 06**：日冻结数据模式字

```rust
struct FreezeModeConfig {
    timed_mode: TimedFreezeMode,        // 04 00 09 02，定时冻结
    instant_enabled: bool,              // 04 00 09 03，瞬时冻结是否启用
    appointment_mode: Option<AppointmentFreezeMode>,  // 04 00 09 04，约定冻结
    hourly_enabled: bool,               // 04 00 09 05，整点冻结
    daily_enabled: bool,                // 04 00 09 06，日冻结
}

enum TimedFreezeMode {
    Disabled,
    Monthly { day: u8, hour: u8, minute: u8 },    // 99 DD hh mm
    Daily { hour: u8, minute: u8 },               // 99 99 hh mm
    Hourly { minute: u8 },                        // 99 99 99 mm
}

impl TimedFreezeMode {
    /// 转换为协议中的 04 00 09 02 字节（位图编码）
    fn to_protocol_byte(&self) -> u8 {
        match self {
            TimedFreezeMode::Disabled => 0,
            TimedFreezeMode::Monthly{..} => 1,
            TimedFreezeMode::Daily{..} => 2,
            TimedFreezeMode::Hourly{..} => 3,
        }
    }
    
    fn from_protocol_byte(byte: u8, params: [u8; 4]) -> Self {
        let period_bits = byte & 0x03;
        match period_bits {
            0 => TimedFreezeMode::Disabled,
            1 => TimedFreezeMode::Monthly {
                day: params[2],      // DD
                hour: params[1],     // hh
                minute: params[0],   // mm
            },
            2 => TimedFreezeMode::Daily {
                hour: params[1],
                minute: params[0],
            },
            3 => TimedFreezeMode::Hourly {
                minute: params[0],
            },
            _ => unreachable!(),
        }
    }
}
```

#### 4.6.4 结算日冻结数据存储

根据协议，结算日冻结数据有两种规模：
- **日冻结**：上 62 次（DI0=01-3E，3EH=62）
- **月冻结**：上 24 个结算日（DI0=01-18，18H=24）

```rust
// 结算日索引枚举
enum SettlementIndex {
    Current,                // DI0=00，当前
    Previous(u8),           // DI0=01-18（月）或 01-3E（日），上N次
}

// 冻结数据按 (trigger_type, settlement_index) 分别存储
// trigger_type=05（定时冻结）时：
// - settlement_index=00：当前值
// - settlement_index=01-0C：最近12次（月/日/时冻结混合）
// trigger_type=月冻结特殊标识时：
// - settlement_index=01-18：上24个结算日
```

**重要**：日冻结和月冻结的历史数据**不在内存中全量保留**，只保留当前和最近 1-2 次在内存，其余落库。读取 DI0>02 的历史冻结数据时直接查 SQLite。

（字段命名与类型仅为设计草案，实现时以 `references/data-identifiers.md` 的完整字段清单为准逐项补全，不要遗漏任何一个已在协议中定义、被判定为"本版本需要支持"的 DI。哪些 DI 是首版必须支持、哪些可以后续迭代，见第 7 节范围划分。）

### 4.8 持久化方案：配置文件 vs SQLite

两者分工，不是二选一：**配置文件负责"部署配置"（一次性读入、人工维护、版本控制友好），SQLite 负责"表运行时数据"（会变化、需要查询、需要跨重启持久化）**。

**配置文件（TOML）**：表实例模板、地址区间生成规则、transport/tick/admin 监听参数。特点是启动时读一次，不回写，适合 diff 和环境间迁移。

**SQLite**：

| 表 | 内容 | 写入频率 |
|---|---|---|
| `meters` | 地址 + 当前完整参量（时段表/密码/结算日/冻结模式字等） | 写命令生效时 |
| `energy_registers` | `(address, energy_kind, rate, settlement_day) -> value` | 定期批量 flush，非每 tick |
| `max_demand` | `(address, demand_kind, rate) -> (value, occurred_at)` | 更新时 |
| `freeze_snapshots` | `(address, trigger_type, category, occurrence_idx, ts, payload)` | 冻结触发时（低频，可即时写） |
| `event_records` | `(address, event_kind, sub_kind, occurrence_idx, start, end, payload)` | 事件生成时（低频，可即时写），**包含故障事件和编程记录** |
| `event_summary` | `(address, event_kind, sub_kind) -> (total_count, total_duration)` | 事件计数累加时 |
| `load_profile_records` | 负荷记录时序数据（按通道/时间查询） | 每次采样生成时即时写 |

**不持久化的部分**：瞬时变量（电压/电流/功率等）每 tick 都在变，属于纯内存态，按需重新计算即可，不落库。

**避免 SQLite 成为瓶颈的关键点**：
- 电能寄存器的内存值才是权威态，SQLite 只做定期快照（按时间或电量增量阈值触发）+ 进程优雅退出时的最终 flush，不是每次变化都写——这也贴近真实电表 EEPROM 定期刷新而非逐脉冲写闪存的行为。
- 不让 2000 个 MeterActor 各自持有数据库连接抢锁写入，统一由一个独立的 `PersistenceWorker` task 消费所有 Actor 通过 mpsc 提交的落盘请求，攒批后做事务写入，SQLite 开 WAL 模式减少锁竞争，Actor 的 tick 循环不被磁盘 I/O 阻塞。
- 冻结/事件类数据量级远小于电能量的每 tick 更新，可以即时写，不需要攒批。

**技术选型**：`sqlx`（async，原生适配 tokio，带连接池）优先；不需要 async 特性也可用 `rusqlite` 配合独立线程跑 Worker。

这一节同时明确回答了第 8 节"开放问题 4"（是否需要持久化）：**需要，SQLite 就是持久化落点，进程重启时按地址查库优先恢复历史状态，查不到才用配置模板生成初始态**。

## 4.7 负荷记录数据标识定义（DI3=06）

负荷记录与冻结快照不同，是按时间序列追加的历史数据，读取时需要指定时间范围。根据协议 A.7 负荷记录数据项编码表：

| DI3 | DI2 | DI1 | DI0 | 数据名称 | 数据格式 | 字节数 |
|-----|-----|-----|-----|---------|---------|-------|
| 06 | 10 | 01 | 01-03/FF | A/B/C 相电压 | XXX.X V | 2 |
| 06 | 10 | 02 | 01-03/FF | A/B/C 相电流 | XXX.XXX A | 3 |
| 06 | 10 | 03 | 00-03/FF | 总/A/B/C 相有功功率 | XX.XXXX kW | 3 |
| 06 | 10 | 04 | 00-03/FF | 总/A/B/C 相无功功率 | XX.XXXX kvar | 3 |
| 06 | 10 | 05 | 00-03/FF | 总/A/B/C 功率因数 | X.XXX | 2 |
| 06 | 10 | 06 | 01-04/FF | 正向/反向/组合1/组合2 有功总电能 | XXXXXX.XX kWh | 4 |
| 06 | 10 | 07 | 01-04/FF | 第1-4象限无功总电能 | XXXXXX.XX kvarh | 4 |
| 06 | 10 | 08 | 01-02/FF | 当前有功/无功需量 | XX.XXXX kW/kvar | 3 |

**DI 字段说明**：
- **DI3 = 06**：固定表示负荷记录
- **DI2 = 10**：固定值（协议特殊编码，表示标准负荷记录数据块）
- **DI1 = 数据类型编码**：01 电压/02 电流/03 有功/04 无功/05 功率因数/06 电能/07 四象限电能/08 需量
- **DI0 = 相别或子类型**：00 总/01 A相/02 B相/03 C相/04 四象限，FF 表示通配全部

**注意**：负荷记录的 DI 编码**不严格按通道号扩展**，不同于其他数据项。所有负荷记录共用 DI2=10 标识，通过 DI1（数据类型）+ DI0（相别）组合来区分具体数据项。

**读取命令格式**（11H）：
```
DATA = DI0 DI1 DI2 DI3 + 起始时间(5字节) + 结束时间(5字节)
时间格式：mm hh DD MM YY (BCD)
注意：DATA 区的时间也需要做 +33H 偏移
```

**响应格式**：
```
DATA = DI0 DI1 DI2 DI3 + 块数m(1字节) + 数据块序列
数据块 = 时间(5字节) + 数据项内容(N字节)
```

**超长响应处理**：如果时间范围内的记录数量导致响应 >200 字节，首帧返回前 N 条 + 设置 C 的 D5=1，剩余部分用 12H 续传（与事件记录一致）。

## 5. 关键时序

### 5.1 读命令处理时序

```
主站 --读命令帧(11H)--> Transport 拆帧/解密码前偏移 --> Router 按地址查表
    --> MeterActor.cmd_rx --> on_protocol_command
    --> 定位DI字段 --> 组装响应DATA(+33H) --> 延迟模拟Td --> reply_tx
    --> Router 转发回原连接 --> Transport 编码发送
```

### 5.2 定时冻结自动触发时序（无主站参与）

```
全局tick广播 --> 每个MeterActor.on_tick
    --> 走时/负荷/累加/需量/事件 五步执行完毕
    --> 检查冻结调度条件是否满足（读freeze_mode_word配置的周期）
    --> 满足 -> 生成FreezeSnapshot -> 写入对应RingBuffer（覆盖最旧记录）
```

之后主站随时用 16H 冻结命令查询或直接读 05 类 DI，都能读到最新自动生成的快照，无需主站主动触发。

### 5.3 Admin 批量修改时序

```
调用方 --JSON批量命令(target=address_range)--> Admin监听
    --> 复用Router的地址匹配逻辑展开为多个MeterHandle
    --> 逐个投递 EngineMsg::AdminCommand 到各自mpsc队列（不等待全部完成再返回，逐个ack或汇总返回，视接口设计）
```

## 6. 非功能需求

- **并发规模**：稳定运行 2000 个 MeterActor + 若干 Transport 连接，内存/CPU 占用需可预期（每个 Actor 状态量级评估后给出预算，作为开发中的一项验证任务，而非事先假设）。
- **确定性**：同一份命令序列重放，响应结果与顺序应可复现（这是选择 Actor 串行模型而非共享锁的直接目的），便于写回归测试。
- **可观测性**：建议引入 `tracing`，关键事件（命令处理、冻结触发、事件生成、admin操作）打点，且支持按表地址过滤日志，2000表并发时定位问题依赖这个。
- **可测试性**：Frame Codec 是纯函数模块，优先补全单元测试（对照 skill 参考文件的 worked example）；MeterActor 的仿真逻辑（脉冲累加、滑差窗口、冻结调度）建议单独抽出可脱离 tokio 运行时测试的纯逻辑函数，Actor 只做消息编排。
- **配置友好性**：批量生成 2000 表实例的模板机制是刚需，不是锦上添花，应作为第一版就要支持的能力，而非事后补充。

## 7. 开发阶段划分（建议里程碑，供 AI 辅助开发按序推进）

- 脉冲累加模型、时段表费率查询、最大需量滑差窗口

- 冻结调度（定时+瞬时）与冻结数据环形缓冲
- 补全写命令（14H）、密码校验、冻结命令（16H）、清零类命令

**阶段三：多通道接入（单表）**
- SerialChannel、TcpChannel 实现，验证同一块表可以同时被两种通道访问，命令串行处理、响应顺序正确

**阶段四：多表并发（Registry/Router/2000表）**
- MeterRegistry + 地址路由（精确/通配/广播三种）
- 全局 tick 广播
- 配置模板化批量生成 2000 表实例
- 压测：验证 2000 表并发下的资源占用与响应延迟

**阶段五：Admin 调试通道**
- 单表 admin 命令
- 批量 admin 命令（复用 Router 地址匹配）

**阶段五点五：持久化（SQLite）**
- SQLite schema 建表（meters / energy_registers / max_demand / freeze_snapshots / events）
- `PersistenceWorker` task：mpsc 收敛落盘请求，批量事务写入，WAL 模式
- 启动恢复逻辑：Registry 生成表实例前先查库，命中则恢复、未命中则按模板生成
- 电能寄存器定期 flush 策略 + 优雅关闭时最终 flush

**阶段六（可选/后续）**
- 只读查询旁路快照优化（若压测证明 Actor 串行处理成为瓶颈再实施）
- 负荷记录（DI3=06）历史存储与检索
- 更多异常场景注入能力（断电重启、时钟漂移超限等）

## 8. 开放问题与已解决方案

### 8.1 已解决的问题

1. ✅ **是否需要持久化** - **已定案，见 4.8 节**：采用 SQLite 持久化电能寄存器/最大需量/冻结数据/事件记录/参量，配置文件只管部署层面的模板与启动参数，进程重启时优先从库恢复。

2. ✅ **DI 数据字典来源** - **已明确**：复用 `../spec-engine/schema/dlt645-2007/dlt645.yaml`，该YAML包含所有DI的编码、名称、长度、格式等完整定义，无需重复维护。

3. ✅ **DI 读写属性定义** - **已明确**：在 spec-engine 的 YAML 中补充 `access` 和 `requires_auth` 两个字段，未显式标注的DI按DI3自动推断默认值（见 `docs/yaml_schema_extension.md`）。

4. ✅ **仿真算法** - **已明确**：脉冲累加、滑差窗口、时段表查询等核心算法已详细定义（见 `docs/simulation_algorithms.md`）。

### 8.2 仍需开发中拍板的问题

1. **改通信速率命令（17H）对串口的实际影响**：
   - **建议方案**：默认只在表状态里记录"生效速率"，不真实切串口硬件参数
   - **例外情况**：如果配置文件中某串口只挂了唯一一个地址，且 `allow_baud_change=true`，则允许真实切换
   - **实施时机**：阶段三（多通道接入）开发时决策

2. **通配地址查询多表命中时是否都应答**：
   - **建议方案**：默认全部应答（符合协议规范）
   - **可选配置**：`wildcard_response_mode = "all" | "first" | "warn"`

   - **示例**：`initial_energy_range_kwh = [100.0, 5000.0]`（模拟1-2年表龄）
   - **实施时机**：阶段四（多表并发）开发时可调整

## 11. 数据库表结构详细设计（sqlx + SQLite）

### 11.1 连接与初始化

```rust
let pool = SqlitePoolOptions::new()
    .max_connections(4)              // 单一 PersistenceWorker 串行使用，连接数不需要很大
    .connect_with(
        SqliteConnectOptions::new()
            .filename(&config.persistence.db_path)
            .create_if_missing(true)
            .journal_mode(SqliteJournalMode::Wal)   // 减少写锁竞争

            .busy_timeout(Duration::from_secs(5)),
    )
    .await?;

```

`sqlx::migrate!` 会自动维护一张 `_sqlx_migrations` 表记录已执行的迁移版本，无需手动建版本表。

### 11.2 数值存储约定

- **电能量/功率类小数值**：SQLite 无原生 decimal 类型，为避免浮点误差，统一按协议精度（通常2位小数）**放大100倍存成 `INTEGER`**（如 123456.78 kWh 存成 `12345678`），比存 `TEXT` 省空间、比存 `REAL` 精确。读出后再按精度还原，规则在代码里统一封装成 `to_fixed_point()` / `from_fixed_point()` 两个函数。
- **结构复杂、查询需求低的字段**（如完整时区表/日时段表、负荷模型参数）：用 `TEXT` 存 JSON（`sqlx` 的 `Json<T>` 包装类型，配合 `serde` 直接序列化/反序列化 Rust 结构体，不需要手写JSON拼接）。
- **时间**：统一存 Unix 毫秒时间戳（`INTEGER`），不存字符串日期，避免时区解析歧义；转换用 `chrono`。

### 11.4 表结构设计要点说明

- **`WITHOUT ROWID`**：这几张表的主键都是天然唯一且用于等值/范围查询的复合键，用 `WITHOUT ROWID` 省掉隐藏 rowid 索引，对这种以主键查询为主的表通常更省空间、查询更快。`freeze_snapshots`/`event_records` 若后续需要按自增ID做增量同步之类需求，再评估是否改回普通表+`INTEGER PRIMARY KEY`。
- **冻结/事件用 UNIQUE 复合主键实现环形缓冲**：不需要在应用层写"删除最旧记录"的逻辑，`INSERT ... ON CONFLICT(...) DO UPDATE` 一条语句即完成"有则覆盖、无则插入"，`occurrence_idx` 的滚动分配（比如新快照该占 01 还是把 01-11 依次后移到 02-12）由 `MeterActor` 在生成快照前算好目标 slot 编号再落库，数据库只管存。
- **`event_summary` 与 `event_records` 分离**：因为协议里 DI0=00 返回的是"总次数+总时长"这种持续累加的计数器语义，和 DI0=01..0A 的"最近N次明细快照"语义完全不同，不适合塞进同一张表，分开建表查询逻辑更直接。
- **编程记录统一归入事件记录**：编程记录（DI3=03, DI2=30）本质上是操作类事件，与失压/欠压等故障类事件共用 `event_records` 表，通过 `event_kind`（DI2）区分类型，`payload_json` 根据不同事件类型存储不同字段（故障类存能量增量和持续时长，编程类存操作者代码和修改前后的值）。
- **JSON 字段的取舍原则**：只有"结构复杂、更新频率低、查询时通常整体取用不需要按内部字段过滤"的内容才用 JSON（时区表、密码组、负荷模型参数、快照/事件明细载荷）；凡是需要按值做 `WHERE`/索引/聚合查询的字段（地址、能量类型、费率、结算日、时间）都拆成独立列。

## 12. 负荷记录（DI3=06）完整设计（补充章节）

### 12.1 与冻结快照的区别

| 特性 | 冻结快照（DI3=05） | 负荷记录（DI3=06） |
|-----|------------------|------------------|
| 存储结构 | 环形缓冲，固定槽位（定时12次/瞬时3次） | 时间序列，无上限（实际受存储容量限制） |
| 查询方式 | 按 DI0（第几次）直接索引 | 按时间范围查询（起始-结束时间） |
| 数据内容 | 快照时刻的完整状态（电能/需量/瞬时量） | 特定数据类别的采样值（电压/电流/功率等） |
| 采样周期 | 由冻结模式字配置，统一周期 | 按通道+数据类别各自独立配置间隔 |
| 覆盖策略 | 滚动覆盖（新快照替换最旧槽位） | 追加不覆盖（除非手动清理或达到存储上限） |

### 12.2 采样调度逻辑（在 on_tick 第 7 步）

```rust
// MeterState 中需要维护的状态
struct LoadProfileSchedule {
    channels: HashMap<(LoadChannel, DataType), NextRecordTime>,
}

struct NextRecordTime {
    interval_minutes: u16,        // 从配置 04 00 0A xx 读取
    next_trigger_time: DateTime<Utc>,
}

// tick 中的调度检查
fn check_load_profile_schedule(&mut self) {
    for ((channel, data_type), schedule) in &mut self.load_profile_schedule.channels {
        if self.virtual_time >= schedule.next_trigger_time {
            // 生成一条负荷记录
            let record = self.generate_load_profile_sample(channel, data_type);
            
            // 立即提交到 PersistenceWorker
            self.persist_tx.send(PersistRequest::WriteLoadProfileRecord {
                address: self.address.clone(),
                record,
            }).await.ok();
            
            // 更新下次采样时间
            schedule.next_trigger_time += Duration::minutes(schedule.interval_minutes as i64);
        }
    }
}

fn generate_load_profile_sample(&self, channel: &LoadChannel, data_type: &DataType) -> LoadProfileRecordRow {
    let payload = match data_type {
        DataType::Voltage => {
            // DI2=01：读取当前 A/B/C 相电压
            json!({
                "phase_a": self.instant.voltage_a,
```

### 12.3 读取命令处理（11H + DI3=06）

```rust
fn handle_read_load_profile(
    &self,
    di: [u8; 4],
    start_time: DateTime<Utc>,
    end_time: DateTime<Utc>,
) -> Result<Vec<u8>, ReadError> {
    // 1. 从 SQLite 查询时间范围内的记录
    let records = self.query_load_profile_from_db(di, start_time, end_time).await?;
    
    // 2. 编码为协议格式
    let mut data = di.to_vec();
    data.push(records.len().min(255) as u8);  // m = 块数
    
    for record in records {
        // 每个数据块 = 时间(5字节) + 数据项内容
        data.extend(encode_bcd_time(record.recorded_at));  // mm hh DD MM YY
        data.extend(record.payload_bytes);
    }
    
    // 3. 检查是否超长
    if data.len() > 200 {
        // 暂存待续传缓冲，首帧返回前 N 条
        self.pending_continuations.insert(
            (connection_id, di),
            PendingContinuation { full_data: data.clone(), /* ... */ }
        );
        data.truncate(200);
        // 控制码需要设置 D5=1
    }
    
    Ok(data)
}
```

### A.1 负荷记录超长响应处理
**问题**：读负荷记录时，如果时间范围内记录数超过 L≤200 限制如何处理？  
**答案**：首帧返回前 N 条 + 设置 D5=1（有后续数据），然后用 12H 续传。

### A.2 冻结命令响应格式
**问题**：冻结命令（16H）成功/失败的响应 DATA 是什么？  
**答案**：执行成功回复 L=0（空DATA），执行失败 L=1 + 1 字节错误码。

### A.3 广播冻结语义
**问题**：广播冻结命令（16H + 999999999999H）对表的影响是？  
**答案**：每个表立即执行一次冻结（相当于瞬时冻结），**不修改**表内的冻结模式字配置。

### A.4 广播校时DATA格式
**问题**：广播校时（08H）的 DATA 区是否做 +33H 偏移？  
**答案**：**需要做 +33H 偏移**。所有 DATA 区统一规则，无例外（之前认为读通信地址13H不做偏移是特例，但那是因为13H的DATA为空，响应时地址字节不属于DATA区）。

广播校时 DATA = 6 字节 `ss mm hh DD MM YY`（BCD，低字节先传），编码时需要 +33H，接收方解码时 -33H。
**问题**：数据块响应的 `m`（子项数量）是 1 字节，如果实际超过 255 如何处理？  
**答案**：协议保证不会出现通配查询结果 >255 项的情况（规范设计时已限制）。

### A.5 数据块 m 值上限
**问题**：修改密码（18H）的 DATA 结构是？  
**答案**：
```
控制码：C=18H
数据域长度：L=0CH (12字节)
数据域：DI0 DI1 DI2 DI3 + PA0 P00 P10 P20 + PAN P0N P1N P2N
```
- `DI` = 04 00 02 01-0A（对应密码级别 1-10）
- `PA0 P00 P10 P20` = 旧密码，PA0 高半字节=权限等级（00-09），低半字节+P00 P10 P20=密码值
- `PAN P0N P1N P2N` = 新密码，格式同上
- 权限说明：
  - 02 级权限：电表清零、事件清零
  - 04 级权限：写数据、最大需量清零

### A.6 修改密码命令格式
根据协议图片，编程记录的 DI 编码为：
- `03 30 0F 00` = 费率参数表编程总次数
- `03 30 0F 01` = 费率参数表编程记录明细（第 1-N 次）
- `03 30 10 00` = 阶梯表编程总次数
- `03 30 10 01` = 阶梯表编程记录明细
- `03 30 12 01` = 密钥更新记录明细
- `03 30 13 00` = 异常插卡总次数
- `03 30 14 00` = 非法插卡总次数
- `03 32 01-06 xx` = 购电记录（第 1-10 次）
- `03 33 01-06 xx` = 购电金额记录（第 1-10 次）

**存储方案**：编程记录统一归入 `event_records` 表，其中 `event_kind`=DI2（30/32/33 等），`sub_kind`=DI1（0F/10/12 等），`payload_json` 根据不同类型存储：
- 费率参数表编程（30 0F）：操作时间、操作者代码、修改前后的费率值
- 密钥更新（30 12）：操作时间、操作者代码、密钥更新前后状态、新密钥总数
- 购电记录（32）：购电日期、购电次数、购电量、剩余电量
- 购电金额（33）：购电日期、购电金额、剩余金额

写数据/清零操作后需追加对应的编程记录日志到 `event_records` 表。
